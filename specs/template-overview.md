# Template discovery overview

The OpenClaw Templates landing page shows up to eight featured entries and up to eight entries per category. It must not wait for fourteen independent catalog reads (and additional category continuation pages) before rendering.

GET /api/v1/templates/overview?limit=8 returns a single consistent public snapshot:

- complete: true, featured: PackageListItem[], sections: [{ category, items: PackageListItem[] }]. Empty categories are omitted; category order follows the shared taxonomy, followed by other.
- Featured order follows highlighted badge recency, with the same exclusion and English-listing rules as the legacy featured list.
- Categories rank by current installs descending, then package name ascending. They use current package stats, not stale digest stats.
- Public visibility excludes private, deleted, unpublished and blocked packages. Templates also require an available publisher whose current handle matches the package scope.
- Publisher identity and official status are resolved live. Promise caches are query-local only; the next read observes deactivation or badge revocation.
- The request uses the ordinary read rate limit. There is no new response cache and no privileged viewer expansion.
- The snapshot reads at most 1,001 active Template digest rows and 1,001 highlighted badges. If either collection exceeds 1,000, it returns complete: false with empty lists. Publisher and projection reads run in batches of sixteen to remain below the concurrent-I/O limit. A specifically identified native transaction read-byte limit is converted at the HTTP boundary into the same complete: false envelope; unrelated errors still propagate. Consumers must then use the existing paginated path, not rank a truncated catalog.
- limit defaults to eight and accepts integers from one through eight. Existing package/category/search routes remain compatible.

A client can request `include=categoryEntries` to reuse this same public snapshot for a category's “View all”. On a complete snapshot the response may add top-level `completeCategoryEntries: true`. This means **every** returned section contains its full ranked public category list, not just the first `limit` items; featured is still limited. Only the current taxonomy and `other` are sections: a listing in two current categories counts twice and a removed-only category never becomes a section. Expansion uses the rows already projected by the overview, with no additional database reads. It is all-or-nothing: the JSON-serialized `sections` array, including its wrappers, must be at most 256 KiB of UTF-8 and contain at most 256 entries across all sections. When either cap is exceeded, or the option is absent or unrecognized, the legacy limited response is returned with no marker. A `complete: false` snapshot never carries the marker.

The OpenClaw consumer must use one gateway request for an unfiltered overview. Only a marked snapshot can satisfy category navigation without a category read. Otherwise keep the existing paginated category path; search is unchanged. Only an absent endpoint (404) or complete: false authorizes legacy fallback; transport, authorization and rate-limit failures must not be hidden by fan-out retries.

## HTTP startup boundary

The overview must not initialize unrelated publishing, scanning, archive, or package-management HTTP implementations before serving its read. Register the complete route table eagerly, but resolve unrelated implementations only after their matching route passes the existing ingress and quota middleware. Preserve every method/path/prefix and pass the original request and action context through so request-scoped authentication and rate-limit deduplication remain intact. Module-load and handler failures must propagate; do not cache rejected loader promises or turn them into empty successful catalogs.

Keep the overview query in a read-only module separate from package publication and moderation initialization. Its bounded selection, current publisher/official state, live statistics, transaction-budget fallback, and anonymous response contract remain unchanged. This startup optimization introduces no response cache, visibility delay, quota bypass, or install authority. Package metadata/version/artifact and Skill Card GET registrations resolve their existing leaf handlers rather than the aggregate V1 registration barrel, so reading a Template does not initialize unrelated route implementations. The canonical handlers still own all viewer, moderation, exact-version and download checks. Internal exact-version selections must retain manual moderation and legacy static-scan inputs until the shared archive streamer applies download policy; the public Template projection intentionally omits private reviewer notes and is not a complete download-authority object.

Template metadata, exact-version, and npm artifact download GETs use a read-only implementation graph: publication schema compilation must not run merely to display a Template. This covers scoped and unscoped Template names, for anonymous readers and for readers identified by a current API token. They call the same current-viewer queries, public projections, quota middleware, and shared security-checked archive streamer as the canonical router, passing the token's user as the viewer. Cookie-backed sessions, credentials that do not resolve to a current API token, non-Template families, router endpoints that share the unscoped namespace, and unsupported/legacy routes stay with the canonical router. A fallback may join a query promise only within the same action context, original Request, viewer, package and exact version; it is not a cross-request response cache. Nulls and failures must not leak to later requests. No private visibility, install permission, integrity or moderation check is relaxed. Local development impersonation is not consulted on this path: an anonymous request reads as anonymous, where the canonical router would adopt the impersonated development user. This never applies in production and only narrows visibility.

### Website detail expansion

The opt-in `?view=template-detail` adds only the open document and LLM analysis for the current published Template. Select them in the same viewer-authorized database snapshot as the metadata and tags. Check the package and latest-release identity before applying download policy to the full release; the public release projection cannot authorize a file read. Never inline private or blocked bytes or analysis, even when the viewer can inspect metadata. Resolve the exact entry from the validated package.json stored at publish, verify its stored size and hash, and apply the normal bounded UTF-8 preview policy. An older envelope without a validated entry point omits the expansion; a storage outage is an error, not an empty preview. Ordinary metadata, explicit file reads, and install clients do not opt in.

## Function module startup boundary

Convex evaluates a function's whole module, with every static import, each time that function runs without a cached result. Constructing the ArkType schemas in `clawhub-schema` takes roughly 0.4 seconds, so a module that statically imports them adds that time to each of its uncached queries and mutations. Before 2026-11-15 the `packages`, `skills`, `publishAttempts` and several smaller modules did so through the `clawhub-schema` barrel, and an uncached package read cost about 0.45 seconds per query regardless of what it read.

Modules that serve reads should therefore not statically import ArkType. Import validation-free constants and helpers from their own `clawhub-schema/<name>` entry points, and load schemas with `await import()` inside the publication or validation path that needs them. `convex/lib/schemaLibraryImports.test.ts` enforces this for the modules it lists (`packageReadHttp`, `packages`, `publishAttempts`, `schema`, `skills`) by walking their static import graphs against the built `packages/schema/dist`; add a module there when it is cleaned up. HTTP routers that validate request and response bodies may import the schemas, because the route table loads them on demand.

As of 2026-11-15, 23 other top-level modules still reach ArkType statically and still pay this cost, among them `securityScan`, `catalogFeed`, `promotionsFeed`, `managedMcp`, `maintenance`, `pluginCategoryRefresh`, `githubSkillSync`, `skillsShCatalog` and `skillsShClaims`. They are not covered by the guard.

### Measurement, 2026-11-15

Production, Axiom `clawhub` dataset, uncached executions over 30 minutes: `skills` queries p50 433 ms (509,275 runs), `packages` queries p50 488 ms, `publishAttempts` mutations p50 451 ms, against `publishers` queries p50 30 ms and `tokens` queries p50 23 ms, which never imported the schemas.

Local, same Mac Studio. Evaluating the bundled module once, before and after: `packages` 383 ms to 12 ms, `skills` 321 ms to 6 ms, `promotions` 495 ms to 1 ms. Against two local Convex backends, base and candidate, with a new name on every request so no query result was cached: unscoped package lookup 0.60 to 0.72 s before and 0.19 to 0.24 s after; skill lookup 0.51 to 0.59 s before and 0.19 to 0.28 s after. Both are misses that fall back to the canonical router, so they still include loading it. A Template hit on the narrow path was not measured locally because no Template was seeded.

## Measurement, 2026-11-04

All runs originate on the same Mac Studio with anonymous requests, no client data cache, the same explicit no-cache request header and no artificial delay. Time begins before catalog requests and ends after the complete JSON payload is available. These measure catalog data readiness, not process startup or browser navigation/paint. No cache-busting query is used: server query caching is part of real behavior.

Production baseline reproduces the actual OpenClaw overview: fourteen concurrent featured/category reads, following every continuation cursor and then selecting eight per section. It requires fifteen HTTP responses because other has 129 entries. Fresh runs: 3082.142, 2076.383, 1498.663, 2178.957, 1567.515 ms. Average: 2080.732 ms. Required production target: at most 1040.366 ms.

Local verification uses an isolated real Convex installation at 127.0.0.1:3410/3411 with 152 published public-corpus fixtures, two publishers, eight highlighted templates, research=12, productivity=11 and other=129. The unchanged implementation and candidate use the exact same database. A preliminary unpublished fixture was rejected and its timing discarded.

Unchanged local average: 1044.988 ms (five runs). Initial candidate average: 228.742 ms. Final bounded-concurrency candidate: 448.711, 205.216, 195.451, 197.439, 189.070 ms; average 247.177 ms, a 76.3% reduction. Exact selected-name parity was checked for all fourteen featured/category selections, including empty categories. Runtime tests additionally cover hidden/private/spoofed/unpublished records, publisher deactivation, live stats and badge changes, HTTP validation, a genuinely visible 1,000-row catalog and bounded-catalog fallback.

A native local stress check expanded each of the 152 package changelogs to 120,000 bytes. The direct query reached the actual 16 MiB read limit; the HTTP action returned 200 with complete: false and empty lists. All original fixture content was restored and the temporary helper removed from source and generated API before final measurement. The unit HTTP error-boundary test simulates the same platform error and separately asserts unrelated failures propagate.

Production release remains subject to exact-head review and CI, followed by the same five-run production comparison and live route verification. Backend availability alone does not activate the new path in older OpenClaw clients.
